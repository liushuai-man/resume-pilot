# ResumePilot V2.0 开发路线图

**文档性质：** 动态执行文档  
**对应产品文档：** [产品基线](../product/product-baseline.md)
**当前目标：** 验证“JD 分析—简历优化—效果验证—面试训练—个人能力复盘”求职闭环，而不是一次性完成全部功能。

## 1. 维护规则

本路线图允许频繁调整，不把第一次设计当作最终答案。

- 每完成一个可使用的纵向切片，就进行一次真实简历和真实 JD 验证
- 根据用户价值、技术风险和验证结果重新排序，不按模块机械开发
- 每次只保持一个主要开发目标，其他需求进入候选池
- 产品范围和验收口径写入产品文档；开发顺序、方案实验和复盘记录在本文档
- 评分规则、Prompt、JobProfile 和 Rubric 必须带版本号，确保调整后结果可追踪
- 新功能先证明闭环价值，再补充复杂自动化、向量检索或爬虫

每轮迭代结束记录：

| 项目 | 内容 |
| ---- | ---- |
| 本轮假设 | 希望解决的用户问题及预期结果 |
| 最小实现 | 本轮实际交付的最小闭环 |
| 验证样本 | 使用了哪些岗位、JD 和简历 |
| 观察指标 | 完成率、修改采纳率、评分变化、面试完成率等 |
| 发现的问题 | 用户困惑、错误结果、性能或成本问题 |
| 调整决定 | 保留、修改、降级、推迟或删除 |
| 下一轮目标 | 下一项最值得验证的能力 |

## 2. V2.0 最终呈现

V2.0 不再以零散 AI 工具为中心，而以一次“目标岗位求职任务”为中心：

```text
创建或导入简历
      ↓
粘贴 JD → 确认岗位画像 JobProfile
      ↓
ATS 基础分析 + JD 岗位匹配
      ↓
定位问题 → 局部优化 → 用户确认
      ↓
记录优化历史 → 对比效果并支持撤销
      ↓
基于同一 JobProfile 和不可变简历快照进行模拟面试
      ↓
生成能力报告 → 返回简历或继续专项训练
      ↓
个人中心沉淀评分趋势与用户能力画像
```

当前导航结构：

- 我的简历：创建、导入、编辑、预览，以及查看优化历史和撤销修改
- 目标岗位：保存 JD、确认岗位画像和查看匹配结果
- 模拟面试：直接进入面试准备/进行界面，在同一路由内选择目标岗位与当前简历后开始训练；系统在开场时锁定不可变快照
- 面试记录：只查看面试训练与报告；简历优化历史和岗位分析记录分别归属“我的简历”和“目标岗位”
- 个人中心：通过导航栏头像进入，展示跨记录聚合的评分趋势、能力画像和账户信息

导航与路由规则详见 [信息架构与界面规范](../design/information-architecture.md)。普通管理页面始终显示全局导航；简历编辑器和模拟面试状态机使用精简任务工具栏；登录页与 PDF 渲染页不显示全局导航。ATS、内容质量与岗位匹配属于“目标岗位”的二级能力，不单独占用一级导航。

## 3. 开发阶段

路线图采用纵向切片。每一阶段都必须形成用户可体验的结果，阶段顺序可根据验证结果调整。

### 阶段 0：稳定简历基础能力

**目的：** 确保后续所有分析引用同一份可靠的简历数据。

**状态：** 进行中

- 统一 `ResumeDocument` 数据结构
- 编辑器、首页、在线面试复用同一预览内核
- 修复 A4 分页、模板渲染和 PDF 导出一致性
- 建立关键模板与分页的回归样本

当前实施记录：

- 已统一编辑器、首页、在线面试的 React 预览内核
- 已启动 PDF 导出链路统一：Puppeteer 打印专用只读预览路由，不再使用独立旧 HTML 模板
- 已将分页算法从预览组件抽离为纯模块，并补充整段换页、列表跨页顺序/唯一性与超高条目保留的固定回归样本；真实浏览器预览与 PDF 逐页视觉一致性仍需在本地服务、数据库样本和登录态就绪后执行

**完成表现：** 同一简历在编辑器、只读预览和 PDF 中内容及分页基本一致。

### 阶段 1：JD → JobProfile 最小闭环

**目的：** 建立整个 V2.0 的统一评价标准。

**状态：** 进行中

- 用户粘贴并保存 JD
- AI 提取岗位名称、职级、行业、职责、必备能力、加分项和关键词
- 每项要求保留 JD 原文证据
- 用户可以修改并确认岗位画像
- 保存 `parserVersion`、`promptVersion` 和 JobProfile 版本

**页面呈现：** 左侧 JD 原文，右侧结构化岗位画像；低置信度字段提示用户确认。

当前实施记录：

- 已完成 JD 保存、列表、删除以及 JobProfile 生成、修改、确认和版本替换流程
- 已保存模型、Prompt、Parser 和 JobProfile 版本信息
- 已提供岗位画像版本列表与切换，明确标记“待确认、当前确认、历史版本”；重新分析会冻结旧草稿，历史版本只读
- 已强制校验职责、必备能力和加分项的证据必须能在 JD 原文中定位
- 低于 70% 置信度的提取项在确认页面标记为“需要重点确认”
- 已建立结构校验、代码块兼容、关键词去重和虚假证据拒绝的解析回归测试
- 待使用多份真实 JD 与实际模型完成产品验收后，再将阶段 1 标记为完成

**验证重点：** 结构化结果是否准确、用户是否理解并愿意确认，而不是模型输出是否看起来丰富。

### 阶段 2：ATS 与岗位匹配

**目的：** 让用户知道简历哪里有问题，以及为什么有问题。

**状态：** 已完成

- ATS 结构分：机器可读性、字段完整性、日期格式和明显无意义文本，只使用可复现规则
- 内容质量分：连贯性、信息有效性、任务—行动—结果表达和上下文一致性，由语义评价 Agent 生成字段级结论与置信度
- 岗位匹配分：能力覆盖、关键词证据、职责相关性和职级匹配，只使用已确认 JobProfile
- 结构分、内容质量分、岗位匹配分独立展示，禁止把“字段填满”呈现为“内容优秀”
- 事实可信度不混入语言质量：院校、公司等实体只有在接入权威数据源后才能标记“已核验 / 未找到 / 待确认”，不能让大模型直接判断造假
- 问题定位到具体 `section / item / field`
- 区分“已匹配、证据不足、能力缺口、待确认”

内容质量 Agent 的评价维度：

- 语言连贯性：是否为完整、可理解的自然语言，而非字符堆叠
- 信息有效性：是否提供求职相关信息，而非空泛自评或无意义填充
- 证据具体性：是否说明任务、行动、技术使用场景和结果
- 上下文一致性：职业目标、技能、教育、经历之间是否明显矛盾
- 表达专业性：是否存在大段重复、口语化占位、夸张但无法定位证据的表述

内容质量 Agent 的输出约束：

- 每项结论必须携带 `section / item / field`、字段原文、理由、严重级别和置信度
- 评价结果保存 `modelVersion / promptVersion / evaluatorVersion`
- 低置信度结论进入“待确认”，不直接扣除或增加最终质量分
- 模型调用失败时只展示 ATS 结构分，不得用字符规则伪装成语义评价
- 结构分、内容质量分和岗位匹配分不合并成一个来源不明的总分

阶段 2 验收数据集必须包含：完整优秀简历、字段齐全但语义无效简历、重复/乱码文本、虚构但语言正常的实体、跨字段矛盾、缺少 JD 证据和不同年限岗位样本。

**页面呈现：** 总览分数只是入口，主要区域展示可定位、可处理的问题清单；点击问题跳转到对应简历字段。

**实现原则：** 确定性规则负责结构分；大模型负责内容质量与岗位语义判断，但必须返回字段定位、理由和置信度；权威数据源负责实体核验。三层结论分别保存、分别版本化。当前单份 JD 与简历对比不强制使用向量库。

当前实施记录：

- 已完成 ATS 基础体检首个纵向切片：用户在目标岗位页选择简历并主动运行分析
- 已建立 `ats-rules-v3-additive` 确定性加分评分器：从 0 分开始，按机器可读性、基本信息、教育信息、经历证据、专业技能和内容表达六个维度获得分数；空白与空壳模块天然不得分
- 已将当前结果明确降级命名为“ATS 结构初检”，展示评价边界；增加重复字符、占位词和键盘乱码等明显无意义文本拦截
- 已完成内容质量评价 Agent 首个纵向切片：独立评价连贯性、信息有效性、证据具体性、上下文一致性和表达专业性，不与 ATS 结构分合并
- 内容质量问题已绑定简历 `section / item / field`、字段原文、理由、建议、严重级别和置信度；低于 70% 的结论标记为“待确认”
- 已保存简历更新时间、内容哈希、模型、Prompt 和评价器版本；简历修改后旧报告标记为过期
- 已强制校验模型引用的字段及证据必须能在简历原文中定位，拒绝模型编造证据；模型失败时不生成替代语义分
- 每个问题均返回明确扣分及 `section / item / field` 定位，可进入编辑器对应模块处理
- ATS 基础分与岗位画像确认解耦；JD 岗位匹配仍要求使用已确认 JobProfile
- 已使用真实模型完成内容质量与岗位匹配固定集校准
- 已完成基于当前已确认 JobProfile 的岗位匹配首个纵向切片：能力覆盖、职责相关性、关键词证据和职级匹配四维独立计分，逐项区分“已匹配、证据不足、能力缺口、待确认”，并保存画像版本、简历更新时间、模型、Prompt 与评价器版本
- 岗位匹配由后端强制选择当前已确认画像；模型引用的简历证据必须能定位到具体字段连续原文，低于 70% 置信度的结论只能进入“待确认”；画像或简历更新后历史报告标记为过期
- 真实模型内容质量固定集已完成 5/5 校准：能够区分优秀内容、语义填充、乱码重复、实体真实性边界和跨字段矛盾；当前模型单样本耗时约 45–73 秒
- 岗位匹配 Prompt 已升级到 `job-match-v2`：技能栏中的裸关键词只能判定为“证据不足”，必须有经历或项目中的使用场景才能判定“已匹配”；该异常样本真实模型复测通过
- 已为结构化评价启用 JSON mode 并限制思考预算，评价器升级到 `1.1.0`；岗位匹配固定集单样本耗时降至约 16–34 秒，后端会将模型未正确标记的低置信度要求强制归一化为“待确认”
- 院校真实性核验作为独立数据能力设计：优先使用可维护的院校标准库，无法命中时只标记“待确认”，不直接判定虚假

### 阶段 3：基于问题的定制优化

**目的：** 从“给一段润色结果”升级为可控的修改工作流。

**状态：** 进行中

- 针对某个 ATS 或匹配问题发起优化
- 展示修改前、建议文本、修改理由和对应 JD 证据
- 支持逐条接受、拒绝和手动调整
- 缺少事实时转为追问用户，不编造经历
- 应用建议前自动创建版本快照

**页面呈现：** 编辑器右侧为诊断与建议面板，接受建议后立即重新评分，并展示变化原因。

**核心指标：** 建议采纳率、采纳后问题解决率、用户撤销率。

当前实施记录：

- 已完成内容质量问题局部优化的首个纵向切片：从问题清单定位到编辑器右侧“诊断与建议”面板，展示问题、字段原文、建议方向、建议文本和修改理由
- 证据具体性不足且用户未提供事实时，先追问任务、行动和结果，不调用模型编造经历；后端拒绝建议中未经提供的数字
- 只允许基于最新且未过期的内容质量报告生成建议；本切片仅支持复制建议并由用户手动确认修改，不在版本快照完成前自动应用
- 已使用真实模型完成首个局部优化固定样本验收：模型仅使用用户提供的 Redis 与延迟数据生成建议，未引入额外事实，单次耗时约 11 秒
- 已补充建议审阅交互：用户可在本地调整建议文本、恢复 AI 原文、明确拒绝或采纳并复制；审阅状态暂不持久化，自动应用仍等待版本快照能力
- 已完成单条内容质量建议的安全应用闭环：事务内先保存 `ResumeVersion` 快照，再按 `section / item / field` 同步更新标准内容与编辑器骨架；目标字段或分析报告发生变化时拒绝覆盖，应用后支持一键恢复，恢复前同样保留当前版本
- 应用建议后会独立重新运行内容质量评价，展示优化前后总分变化及原字段问题是否消失；重新评分失败不回滚已应用内容，可在面板中单独重试
- 已接入岗位匹配“证据不足”问题的定向优化：仅对最新、未过期且字段可定位的报告开放，JD 证据只决定表达重点，不作为候选人事实；缺少真实使用场景时先追问，应用建议沿用版本快照、并发保护与撤销能力。真正的“能力缺口”因没有简历落点，本切片不自动补写
- 岗位匹配建议应用后会基于当前 confirmed JobProfile 自动重新匹配，展示总分变化，并按同一 `requirementId` 判断该要求是否由“证据不足”转为“已匹配”；重新匹配失败不回滚已应用内容，可单独重试
- 已接入 ATS 可定位字段问题的定向修正：后端每次重新执行确定性规则并按 `issueId` 校验问题仍存在，只对白名单内的现有唯一字段开放；缺少真实内容时先追问，应用时创建快照并同步返回 ATS 新分数与问题是否解决。模块缺失、聚合描述和结构问题仍进入普通编辑器，不由 AI 自动补写
- 阶段 3 综合回归补充了“ATS 检测 → 字段定位 → 安全应用 → 确定性重评分”服务链测试，并修复 ATS 问题 ID 随列表顺序变化导致的误判，以及旧简历 `basicInfo.bio` 无法按 `summary` 回写的兼容问题；确定性测试与前后端类型检查已通过。新增 ATS 真实模型固定样本脚本，但外部模型调用需在明确授权数据发送目标后执行
- 已新增 `ResumeOptimizationAction` 持久化优化操作：由后端事务记录内容质量、岗位匹配和 ATS 建议的可信原文、用户最终采用文本、字段定位、来源、快照版本与采纳状态；重评分/重新匹配完成后由后端读取正式分析记录回填前后分数和问题解决状态，版本恢复时同步标记为已撤销，为采纳率、问题解决率和撤销率提供数据基础
- 已为三类模型建议增加短期服务端签名 `suggestionToken`：token 绑定用户、简历、来源、目标问题、字段、原文与 AI 建议，拒绝接口只接受并验证该凭证后写入可信拒绝记录；跨用户、跨简历、过期或篡改凭证均被拒绝，前端不能自行伪造拒绝样本

### 阶段 4：优化历史与恢复

**状态：** 已完成并于 2026-08-12 通过端到端验收。

**目的：** 让用户看得懂每次 AI 优化的效果，并能安全撤销误操作；底层快照只承担恢复和审计职责，不建设通用版本管理产品。

- 在具体简历内展示优化记录时间线：来源、字段、修改前后内容、理由、状态与发生时间
- 展示每次优化前后的 ATS 分、匹配分和已解决问题数量；无可比数据时明确显示“暂无对比”
- 支持撤销已应用的优化，并把撤销本身记录为可追踪事件
- 自动保存内部恢复快照，绑定当时的评分器版本与已确认 JobProfile；快照不作为用户需要管理的独立对象
- 支持按状态或来源进行最小筛选，优先保证问题定位与恢复闭环

**明确不做：** 手动命名版本、版本分支、通用版本树、面向用户的 JSON 差异以及独立一级“版本管理”入口。

**页面呈现：** 使用“优化历史”时间线表达“修改了什么、为什么修改、是否生效、分数如何变化”，并在可撤销记录上提供明确操作。

**完成标准：** 用户可以从一条已应用优化看到证据与效果、执行撤销并刷新后确认内容恢复；失败或重复撤销不会破坏当前简历。

当前实施记录：

- 已提供具体简历内的优化历史页面，支持按来源与状态筛选、分页查看修改前后文本、评分变化和问题解决状态
- 已实现字段级安全撤销：仅当目标字段仍保留应用后的文本时执行恢复，后续手动编辑会触发冲突保护，重复撤销不会覆盖当前简历
- 新应用的内容质量、ATS 与岗位匹配优化会保存修改原因和对应依据；撤销会新增独立事件并关联原优化记录，不再只修改原记录状态
- 拒绝建议时也会从服务端签名凭证写入可信原因与依据；旧凭证仍兼容，前端不能伪造或篡改拒绝记录上下文
- 内部 `ResumeVersion` 仅用于事务恢复和审计，历史 API 与页面不暴露版本 ID、版本树或手动版本管理操作
- 已新增可重复执行的 `pnpm run test:stage4-e2e`：通过真实 HTTP 与 PostgreSQL 验证应用建议、刷新历史、安全撤销、独立撤销事件、重复撤销保护和后续编辑冲突保护；测试用户与简历在结束时自动清理

### 阶段 5：基于 JD 的在线面试

**目的：** 让模拟面试验证岗位能力，而不是随机聊天问答。

**UI 边界：** 全局视觉重构、公开展示页、导航、主题与基础组件已抽离至 [V2.0 UI 设计系统](../design/ui-design-system.md)，审核通过后按独立 UI 切片实施；本阶段只负责在线面试的业务状态机、Rubric、问答与评价闭环，不再在本节重复定义全局样式。

- 开始前选择面试岗位目标和简历版本；岗位目标从已确认的 JobProfile 中选择，默认值为“通用岗位”
- “通用岗位”使用系统内置通用 Rubric，并在面试页和最终报告中明确标记，不能伪装为具体 JD 定向面试
- 根据岗位、行业、职级与简历证据生成 Rubric 快照
- 每道题关联一个或多个能力维度
- 面试过程中只记录问题与回答，不展示评分、评论、答案优劣或改进建议
- 下一题根据预设面试计划、能力覆盖情况和回答内容决定，不依赖尚未生成的正式评分
- 结束面试后，将完整问答记录和 Rubric 快照一次性提交评价流程
- 报告生成阶段再产生逐题证据、分项得分、知识缺口、置信度和综合建议
- 提供可组合的面试工作台，通过左侧导航按需打开简历、JD、面试记录等辅助面板
- 最终报告展示岗位胜任度、能力覆盖和下一步训练建议

**页面呈现：** 答题是稳定的主区域；左侧工作台导航用于切换辅助面板，岗位要求、当前考察维度和简历证据按需出现。提交回答后直接进入下一题，不插入 AI 评论；结束后进入“报告生成中”，完成后统一展示可追溯评价报告。

调整后的面试流程：

```text
选择 JobProfile 与简历版本
        ↓
生成并冻结 InterviewPlan 与 Rubric
        ↓
提问 → 保存回答 → 决定下一题 → 继续提问
        ↓                    ↑
        └──── 过程中不评分、不评论 ────┘
        ↓
用户结束面试 / 达到题目数量
        ↓
完整问答记录 + Rubric → Evaluation Agent 批量评价
        ↓
后端校验并计算总分 → 写入逐题评价与最终报告
        ↓
历史记录保存原始报告 → 个人中心更新聚合画像
```

#### 模拟面试 Agent 流程

阶段 5 采用“面试执行图 + 报告评价图”两条子流程。面试执行图只负责规划、出题和保存问答；报告评价图只在用户结束面试或达到题数后运行。两条流程共享冻结快照和持久化 checkpoint，但评价结果不得回流到尚在进行的面试页面。

```text
开始面试
  ↓
[S1 Context Validator]
校验用户、简历、confirmed JobProfile 与模型配置
  ↓ checkpoint: context_validated
[S2 Snapshot Builder]
冻结 Resume / JobProfile / Rubric 及版本信息
  ↓ checkpoint: snapshots_frozen
[S3 Interview Planner]
生成 InterviewPlan、题数配额与能力维度覆盖目标
  ↓ checkpoint: plan_ready
[S4 Question Planner]
根据计划、覆盖情况和已有问答选择题型、主题与难度
  ↓
[S5 Question Generator]
Technical / Project / FollowUp 生成具体问题
  ↓ checkpoint: question_ready
[S6 Answer Recorder]
幂等保存问题与回答，不评分、不评论
  ↓ checkpoint: answer_saved
继续 ───────────────→ 回到 S4
结束
  ↓
[R1 Transcript Validator]
校验问答完整性、题目关联和冻结快照
  ↓ checkpoint: transcript_validated
[R2 Batch Evaluation]
基于完整上下文生成逐题评价、证据、知识缺口和置信度
  ↓ checkpoint: evaluations_ready
[R3 Report Composer]
后端依据 Rubric 确定性聚合分项分数、总分、优势、薄弱项和训练建议，不调用模型
  ↓ checkpoint: report_composed
[R4 Report Validator]
校验结构、分数边界、证据引用、版本信息和覆盖率
  ↓ checkpoint: report_validated
[R5 Report Publisher]
事务写入最终报告并标记 completed
  ↓
面试记录 / 后续个人中心聚合
```

Agent 职责边界：

| 节点 | 职责 | 明确不做 |
| ---- | ---- | -------- |
| Context Validator | 权限、归属、状态和配置校验 | 不调用模型，不修改快照 |
| Snapshot Builder | 建立不可变事实基线 | 不引用后续被修改的简历或画像 |
| Interview Planner | 分配主题、维度和题数 | 不生成具体题目，不评价候选人 |
| Question Planner | 决定下一题类型、主题、难度和关联维度 | 不产生正式评分 |
| Question Generator | 根据规划生成一题并结构化输出 | 不改变计划配额，不直接保存回答 |
| Answer Recorder | 幂等保存用户回答 | 不调用 Evaluation Agent |
| Batch Evaluation | 完整问答结束后生成逐题评价 | 不发布报告，不更新长期画像 |
| Report Composer | 使用冻结 Rubric 聚合报告 | 不重新评价或补造证据 |
| Report Validator | 确定性校验和一致性检查 | 不用默认分数掩盖失败 |
| Report Publisher | 事务发布报告、记录版本和状态 | 不重新调用模型 |

`FollowUp` 仅是一种问题生成策略，不依赖过程评分。第一版只能依据上一题回答是否含糊、是否缺少具体场景，以及 InterviewPlan 的覆盖缺口决定是否追问。基于正式 `Evaluation` 的薄弱项追问属于面试结束后的专项训练流程，不回流当前面试。

#### 中间节点状态与失败处理

每个可重试节点记录 `nodeKey / status / attempt / inputHash / output / errorCode / errorMessage / startedAt / finishedAt / modelVersion / promptVersion`。状态限定为：

```text
pending → running → succeeded
                  ↘ failed_retryable
                  ↘ failed_terminal
failed_retryable → running（单步重试）
```

失败处理矩阵：

| 失败节点 | 典型原因 | 数据保护与自动处理 | 用户可执行操作 |
| -------- | -------- | ------------------ | -------------- |
| S1 Context Validator | 简历已删除、画像未确认、无权限、缺少模型 | 不创建会话；返回可操作错误 | 重新选择简历/岗位，完善模型配置 |
| S2 Snapshot Builder | 并发修改、序列化失败 | 事务回滚，不产生半冻结会话 | 重新开始；不得沿用不完整快照 |
| S3 Interview Planner | 模型超时、结构化输出失败 | 同一输入自动重试一次；仍失败时允许使用版本化通用计划，但必须明确标记 `fallback` | 重试规划或接受通用计划 |
| S4 Question Planner | 计划状态异常、覆盖统计冲突 | 使用确定性优先级规则选择未覆盖维度 | 重试当前节点；无需重新回答上一题 |
| S5 Question Generator | 超时、限流、JSON 无效 | 自动重试一次；失败时停留在当前进度，绝不创建空问题 | “重新生成本题”；只重跑 S5 |
| S6 Answer Recorder | 网络中断、重复提交、数据库失败 | 使用 `sessionId + questionId` 幂等键；前端保留草稿，重复请求返回同一结果 | “重新提交回答”；不得生成重复答案或跳题 |
| R1 Transcript Validator | 问答缺失、快照损坏 | 标记终止失败；保留原始问答，不进入模型评价 | 查看缺失项；仅数据可恢复时重试 |
| R2 Batch Evaluation | 模型超时、批量结果存在缺失题目或无效评价 | 正常路径只进行一次批量 Agent 调用；后端按 `questionId` 逐题校验。整批自动重试一次后仍仅少量失败时，才进入题目级补偿队列 | 优先“重新批量评价”；必要时再补偿失败题目 |
| R3 Report Composer | 聚合模型失败、输入版本不一致 | 保留全部逐题评价；不得伪造默认报告或默认 60 分 | “重新汇总报告”；只重跑 R3 及下游 |
| R4 Report Validator | 分数越界、证据无法定位、结构不完整 | 报告不发布；返回字段级校验错误 | 修复后重跑 R3，或仅重跑 R4（输入未变时） |
| R5 Report Publisher | 事务/数据库冲突 | 使用 `sessionId` 唯一约束幂等发布；失败不清除会话 checkpoint | “重新保存报告”；只重跑 R5 |

自动重试只适用于超时、限流、临时网络和可解析修复的结构错误，采用有限次数退避；权限错误、资源不存在、快照损坏和证据校验失败不得无限自动重试。任何节点失败都不得清空完整问答，不得退回即时评论模式，也不得用固定分数或模板报告伪装成功。

单步重试规则：

1. 重试请求必须携带 `sessionId / runId / nodeKey / expectedInputHash`，服务端校验当前用户和 checkpoint 版本。
2. 输入哈希未变化时复用所有上游 `succeeded` 输出，只执行失败节点；节点成功后仅使其下游旧输出失效。
3. 输入已变化时拒绝旧 checkpoint 重试，提示从最早受影响节点重新运行，避免混用不同简历、JobProfile、Rubric 或问答版本。
4. 同一节点并发重试只允许一个执行实例；重复请求返回当前运行状态。
5. R2 正常路径只有一个 `batch_evaluation` 节点，一次输入全部问答并一次返回全部评价；`evaluate:q-3` 只用于批量重试仍不完整时的异常补偿，不是常规逐题模型调用。
6. R5 成功后整个报告任务不可再次生成覆盖，只能创建明确的新评价任务或保留审计记录。

#### 前端状态展示与操作

前端不展示内部思维链、Prompt 或模型原始响应，只展示用户能理解和操作的节点状态。

| 页面位置 | 展示内容 | 操作 |
| -------- | -------- | ---- |
| 面试启动区 | “正在校验资料 / 正在准备面试计划 / 准备失败” | 修改选择、重试失败步骤、接受明确标记的通用计划 |
| 答题主区 | “正在准备下一题 / 下一题生成失败”且保留上一题已保存状态 | 重新生成本题；回答保存失败时恢复输入草稿并重新提交 |
| 工作台记录面板 | 每题只显示“当前问题 / 回答保存中 / 已保存 / 保存失败” | 保存失败项可单步重试，不展示评分 |
| 报告生成页 | 节点进度：校验问答、批量评价 `n/m`、汇总、校验、保存 | 重试当前失败节点；R2 支持展开查看失败题目并逐题重试 |
| 面试历史页 | `生成中 / 部分失败 / 生成失败 / 已完成`，以及最近失败步骤 | 继续生成、重试失败步骤、查看已保存问答 |
| 报告详情页 | 完成报告及版本；若未完成则显示 checkpoint 时间线 | 重试当前节点，不把未完成报告显示为 0 分 |

前端操作约束：

- 页面刷新后从服务端恢复任务状态，不依赖组件内 loading 状态推断节点进度。
- 重试按钮显示具体动作，例如“重新生成第 3 题评价”“重新汇总报告”，不使用含糊的“再试一次”。
- 运行中的节点禁用重复操作但允许离开页面；回到历史页后可以继续观察。
- 失败信息对用户说明影响和下一步；技术错误码保留用于诊断，但不直接展示堆栈或模型响应。
- `WorkspaceState`（打开面板、折叠宽度）与 Agent `RunState` 分离，切换面板不得中断、重启或伪造节点状态。

#### 阶段 5 新增验收标准

- 任一问题生成失败后，已保存问答和题目进度保持不变，单步重试不会重复上一题回答。
- 批量评价中一题失败时，其余成功评价保持可复用；重试只调用失败题目。
- 报告汇总或发布失败时，刷新页面仍能看到准确节点、失败原因和可执行重试入口。
- 同一节点重复点击或网络重放不会生成重复问题、重复答案或重复报告。
- 输入快照变化后，服务端拒绝基于旧 `inputHash` 的重试。
- 所有失败路径均不展示即时评分、默认 60 分或未经验证的部分报告。
- 正常完成一场面试时，逐题评价只产生一次批量模型调用；题目级模型调用只允许出现在批量重试仍失败后的补偿路径，并记录额外成本。
- 报告汇总由后端确定性计算，不再调用 Report Agent；相同评价与 Rubric 必须生成相同总分和维度分。常规报告链路因此只有一次 Batch Evaluation 模型调用。
- 报告任务已持久化 `currentNode / failedNode / pipelineState`，前端可展示问答校验、批量评价、确定性汇总和发布进度；失败时按钮使用具体节点名称，不再只显示笼统“重新生成报告”
- 批量评价成功后会保存 `evaluationCheckpoint` 与覆盖冻结简历、JobProfile、Rubric、问题和回答的 SHA-256 `evaluationInputHash`；最终发布失败后重试可直接复用评价。输入哈希变化时旧 checkpoint 自动失效，必须重新执行批量评价
- 已提供 `nodeKey + expectedInputHash` 节点级重试接口：服务端校验当前失败节点、输入版本与执行状态，并通过条件更新抢占唯一执行权；旧节点、过期输入和并发重复点击均返回冲突，不启动额外 Agent 调用
- 回答提交已使用稳定 `submissionId` 实现幂等：网络失败时前端恢复原草稿并复用同一提交标识；服务端重复收到相同提交时返回原 `questionId` 和会话进度，不重复追加回答或跳过问题
- 下一题生成已与回答保存解耦：回答成功后若出题失败，前端只提供“重新生成下一题”，不要求重新提交回答；服务端发现当前题位已有已保存问题时直接返回同一题，响应丢失重试不会重复调用模型或追加问题
- 已支持活动面试刷新恢复：前端只在本地保存活动 `sessionId`，刷新后从服务端恢复问题、回答、当前题位和“下一题待生成”状态；完整业务状态仍以服务端 checkpoint 为准，会话结束、失效或无权访问时自动清理本地指针

- 面试会话状态机与资源加载已分别抽离为 `useInterviewSession`、`useInterviewResources`；路由页面不再直接调用面试、简历、岗位或上传 API，只负责组合工作台布局和连接组件
- 工作台交互状态已抽离为 `useInterviewWorkspace`：面板选择和折叠偏好独立持久化，临时笔记按面试场次仅保存在浏览器，不进入回答、Agent Prompt、服务端 checkpoint 或评分
- 面试报告已拆分为概览、总结与逐题回顾组件；能力概览只使用确定性报告中的正式维度分和题目样本数，未覆盖维度明确标记“未覆盖”，不再根据回答数量推导虚假的表达完整度或完成度
- 面试历史页的数据加载、删除、节点重试与生成中任务轮询已抽离为 `useInterviewHistory`，仅在存在生成中任务且页面可见时刷新；记录卡片独立封装，并展示具体失败节点与对应的重新执行操作

### 阶段 6：个人中心与用户能力画像

**目的：** 将分散在 ATS、岗位匹配、简历优化和模拟面试中的结果沉淀为可持续观察的个人求职数据，而不是只保留一次性报告。

- 通过导航栏头像进入个人中心，不新增拥挤的一级文字导航
- 展示面试次数、平均分、最近得分和阶段趋势
- 展示 ATS 基础分、岗位匹配度和简历优化前后变化
- 根据多次已完成评价聚合技术能力、表达能力、项目深度和岗位适配等维度
- 形成用户能力画像，标注数据来源、样本数、置信度和最近更新时间
- 展示近期活动，并能跳转到对应面试报告、ATS 分析或简历版本
- 支持基础账户信息、模型配置入口和数据隐私说明

**页面呈现：** 顶部是个人信息与求职目标；中部展示核心数据卡片和趋势图；下方展示能力画像与近期活动。样本不足时展示“数据不足”，不生成虚假的精确结论。

个人中心与历史记录的边界：

- 历史记录保存“每一次发生了什么”，负责查看和追溯原始报告
- 个人中心回答“长期来看发生了什么变化”，负责聚合、趋势和用户画像

用户画像约束：

- 只使用用户明确填写的信息及系统正式评价结果
- 不从一次面试推断稳定能力，不推断性格、健康、身份等敏感属性
- 不同岗位画像分开统计，不能把前端岗位得分直接混入后端岗位能力结论
- 删除原始评价后，对应聚合数据必须重新计算

当前实施记录：

- 已完成个人中心首个纵向切片：通过导航栏头像进入，不增加一级导航；实时聚合正式面试、内容质量、岗位匹配与已采纳优化记录，展示面试次数、平均分、最近得分、最新质量分及优化变化
- 能力画像仅在至少两场正式面试后生成，逐维度展示参与聚合的面试场数、题目证据数与置信度；样本不足时明确显示“数据不足”，不从单场结果推断长期能力
- 聚合结果不建立二次持久化缓存，删除原始评价后再次查询会自然重新计算；近期活动可回到对应面试报告、简历编辑器或目标岗位页
- 个人中心已提供数据使用边界说明，仅使用用户主动填写的信息与正式评价，不推断性格、健康或身份等敏感属性
- 已补充最近八场正式面试的可追溯趋势图；点击数据节点可回到原始报告。画像同时按冻结 JobProfile 分组，通用岗位独立统计，不跨岗位混合能力结论
- 账户区已提供模型配置入口，复用现有模型管理与连接校验流程，不在个人中心复制敏感 API Key 状态

### 阶段 7：闭环与质量体系

**目的：** 证明各模块共享数据后确实比独立工具更有价值。

- 从面试薄弱项返回简历证据补充或专项训练
- 记录评分规则、Prompt、模型和 Rubric 版本
- 建立固定 JD/简历/回答评测集
- 增加结构化输出失败降级、限流、重试和成本观测
- 观察用户从 JD 分析到面试报告的漏斗

当前实施记录：

- 面试工作台的正式逐题评价已提供闭环动作：可按问题 `sectionKey` 回到本场简历对应模块补充证据，或携带批量评价产生的知识缺口进入同一简历的新一轮专项训练准备；定位来自已保存问题与正式评价，不进行额外模型推断
- 报告页已展示确定性报告版本与冻结 Rubric 版本，便于回归和审计
- 已移除基于回答长度、关键词生成正式分数的启发式降级，以及单题异常时返回固定 5 分的伪成功路径；正式报告始终执行一次真实批量评价，模型或结构化输出失败时保留报告任务并进入节点重试
- 正式报告已记录批量评价模型、Prompt、Rubric、模型调用次数、checkpoint 复用情况与总耗时；个人中心基于当前正式业务记录展示 JD、确认画像、岗位匹配、完成面试和正式报告的闭环完成量，并明确不将其冒充为行为埋点转化率

## 4. 简历导入的安排

简历导入很重要，但它首先是降低迁移成本的入口，不是 V2.0 的核心评价能力。建议在阶段 1 或阶段 2 验证完成后插入开发，具体优先级由“新用户因重新填写而流失”的实际情况决定。

第一版范围：

- 支持文本型 PDF 和 DOCX
- 提取为统一 `ResumeDocument`
- 原文件预览与结构化结果并排确认
- 用户确认后才创建可编辑简历
- 导入后直接进入 JD/ATS 分析闭环

暂缓范围：扫描件 OCR、复杂双栏还原、表格简历和原排版像素级复刻。

## 5. 在线面试中的简历预览

### 产品判断

简历预览重要，但不是在线面试的核心主功能。它的价值在于给用户和面试 Agent 提供一致的事实背景，避免用户忘记自己简历中的项目细节，并让追问能够指向具体证据。

如果预览占据过大空间，会分散答题注意力；如果完全没有预览，用户又难以理解“为什么问这道题”。因此建议采用按需辅助设计：

- 面试开始前：完整预览并确认本场使用的简历版本
- 面试进行中：默认折叠为侧边栏，展示当前问题关联的简历片段，而不是始终展示整份 A4 简历
- 用户需要时：打开完整只读预览，复用统一 `DocumentPreview`
- 正式模拟模式：可以关闭或限制预览，模拟不能随时翻看简历的真实场景
- 训练模式：允许查看当前问题关联的项目、经历或技能，但不展示答案评价和提示性评论
- 面试报告：点击评价证据可以回到对应简历条目

### 可组合面试工作台

在线面试采用“稳定答题主区域 + 可组合辅助面板”的工作台布局。左侧提供面板导航，顶部或左侧的 `+` 用于添加当前未打开的系统面板。简历预览是工作台中的一种面板，而不是写死在页面中的固定区域。

```text
┌──────────────────────────────────────────────────────┐
│ 面试进度 / 当前考察维度 / 计时                  结束 │
├──────────┬───────────────────────────────────────────┤
│ 对话     │                                           │
│ 简历     │              面试答题主区域               │
│ JD       │             题目 / 回答 / 语音             │
│ 记录     │                                           │
│  +       │                                           │
└──────────┴───────────────────────────────────────────┘
```

第一版工作台提供以下系统面板：

| 面板 | 主要内容 | 行为 |
| ---- | -------- | ---- |
| 简历预览 | 本场锁定的简历版本 | 复用统一 `DocumentPreview`，支持定位并高亮当前问题关联条目 |
| 岗位要求 | JobProfile 的职责、能力和关键词 | 优先展示当前问题对应的评价维度与 JD 原文证据 |
| 面试记录 | 已完成的问题和用户回答 | 点击后定位到对应轮次，不显示评分或评论，不改变 Agent 当前状态 |
| 临时笔记 | 用户个人记录 | 训练模式默认可用，正式模拟模式可关闭 |

交互约束：

- 面板可以打开、关闭、切换和折叠，主答题区域始终保持稳定
- `+` 第一版只能添加系统预定义面板，不支持任意网页、任意组件或无限创建同类窗口
- 打开简历面板时自动定位当前问题关联的项目、经历或技能；没有关联证据时保持普通完整预览
- 训练模式允许查看简历、JD 和提示；正式模拟模式可以隐藏或限制辅助面板
- 模拟面试过程中不展示逐题评价；只有结束整场面试后才能查看统一报告
- 面试期间简历只读，不允许修改本场绑定的简历版本
- 切换面板不能重置问题、计时器、草稿、消息或 Agent 工作流状态

状态设计必须分离：

```text
InterviewState
├── session、currentQuestion、messages、timer
├── interviewPlan、coveredDimensions
├── rubricSnapshot
├── resumeVersionId
└── jobProfileVersionId

WorkspaceState
├── openedPanels
├── activePanel
├── panelWidths
└── collapsed
```

`InterviewState` 是需要持久化和恢复的业务状态；`WorkspaceState` 只是界面布局偏好。工作台布局异常不得影响面试会话恢复。

第一版暂不实现面板拖拽停靠、同时多分屏、任意窗口布局和第三方扩展。只有固定面板模式验证有效后，再评估是否需要向自由 Canvas 演进。

### 优先级

| 能力 | 优先级 | 原因 |
| ---- | ------ | ---- |
| 锁定本场简历版本 | P0 | 保证问题、评价和报告引用同一事实来源 |
| 纯问答模式与完整记录 | P0 | 避免即时评论打断面试节奏，并为结束后的统一评价保留事实 |
| 面试结束后批量评价 | P0 | 使用完整上下文和固定 Rubric 生成一致、可追溯的报告 |
| 左侧工作台导航与面板开关 | P1 | 统一承载简历、JD 和面试记录，保持主答题区域稳定 |
| 显示当前问题关联的简历片段 | P1 | 直接帮助理解追问来源，产品价值高 |
| 打开完整只读简历 | P1 | 有用但不应占据主界面 |
| `+` 添加预定义系统面板 | P1 | 允许用户按需配置工作台，同时控制第一版复杂度 |
| 面试内完整分页与缩放操作 | P2 | 可复用现有组件，不值得单独复杂开发 |
| 自由拖拽、停靠和多分屏 | P3 | 实现成本高，待固定面板模式验证后再决定 |
| 面试时编辑简历 | 不支持 | 会破坏本场评价基准，应在面试结束后修改并创建新版本 |

## 6. 当前建议顺序

在简历预览基础能力已经统一后，下一步建议是：

1. 完成 JD 保存、解析、JobProfile 确认的前后端纵向切片
2. 用少量真实 JD 建立解析评测样本并调整结构
3. 实现第一版确定性 ATS 规则与问题定位
4. 实现岗位匹配，但保持和 ATS 分数分离
5. 根据用户迁移阻力决定插入简历导入，或继续做局部优化
6. 完成优化历史与恢复闭环后，再让在线面试绑定不可变简历快照与 JobProfile，并改为结束后统一评价
7. 积累足够评价记录后实现个人中心聚合数据和用户能力画像

不要提前锁死后续阶段。完成每一项后，都应根据验证记录重新评估下一项是否仍然最重要。

## 7. 候选需求池

以下需求暂不承诺具体版本顺序：

- OCR 与复杂简历导入
- 招聘平台 JD 自动抓取或浏览器插件
- 多份 JD 的岗位聚类和批量投递分析
- 向量检索与长期能力记忆
- 语音面试、摄像头和非语言表现分析
- 企业 HR 端和多人协作

只有当现有闭环出现明确瓶颈或用户反馈证明价值时，再将候选需求移入当前迭代。
