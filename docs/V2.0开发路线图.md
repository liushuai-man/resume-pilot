# ResumePilot V2.0 开发路线图

**文档性质：** 动态执行文档  
**对应产品文档：** [AI 简历助手开发文档](./AI%20简历助手开发文档.md)  
**当前目标：** 验证“JD 分析—简历优化—版本验证—面试训练”求职闭环，而不是一次性完成全部功能。

## 1. 维护规则

本路线图允许频繁调整，不把第一次设计当作最终答案。

- 每完成一个可使用的纵向切片，就进行一次真实简历和真实 JD 验证
- 根据用户价值、技术风险和验证结果重新排序，不按模块机械开发
- 每次只保持一个主要开发目标，其他需求进入候选池
- 产品范围和验收口径写入产品文档；开发顺序、方案实验和复盘记录在本文档
- 评分规则、Prompt、JobProfile 和 Rubric 必须带版本号，确保调整后结果可追踪
- 新功能先证明闭环价值，再补充复杂自动化、向量检索或爬虫

每轮迭代结束记录：

| 项目 | 内容 |
| ---- | ---- |
| 本轮假设 | 希望解决的用户问题及预期结果 |
| 最小实现 | 本轮实际交付的最小闭环 |
| 验证样本 | 使用了哪些岗位、JD 和简历 |
| 观察指标 | 完成率、修改采纳率、评分变化、面试完成率等 |
| 发现的问题 | 用户困惑、错误结果、性能或成本问题 |
| 调整决定 | 保留、修改、降级、推迟或删除 |
| 下一轮目标 | 下一项最值得验证的能力 |

## 2. V2.0 最终呈现

V2.0 不再以零散 AI 工具为中心，而以一次“目标岗位求职任务”为中心：

```text
创建或导入简历
      ↓
粘贴 JD → 确认岗位画像 JobProfile
      ↓
ATS 基础分析 + JD 岗位匹配
      ↓
定位问题 → 局部优化 → 用户确认
      ↓
保存简历版本 → 对比优化前后结果
      ↓
基于同一 JobProfile 和简历版本进行模拟面试
      ↓
生成能力报告 → 返回简历或继续专项训练
```

建议一级入口保持简单：

- 我的简历：创建、导入、编辑、预览和版本管理
- 目标岗位：保存 JD、确认岗位画像和查看匹配结果
- 模拟面试：选择目标岗位与简历版本后开始训练
- 历史记录：查看简历优化记录、面试报告和能力变化

## 3. 开发阶段

路线图采用纵向切片。每一阶段都必须形成用户可体验的结果，阶段顺序可根据验证结果调整。

### 阶段 0：稳定简历基础能力

**目的：** 确保后续所有分析引用同一份可靠的简历数据。

**状态：** 进行中

- 统一 `ResumeDocument` 数据结构
- 编辑器、首页、在线面试复用同一预览内核
- 修复 A4 分页、模板渲染和 PDF 导出一致性
- 建立关键模板与分页的回归样本

当前实施记录：

- 已统一编辑器、首页、在线面试的 React 预览内核
- 已启动 PDF 导出链路统一：Puppeteer 打印专用只读预览路由，不再使用独立旧 HTML 模板
- 下一步补充模板/分页回归样本，并验证浏览器预览与实际 PDF 页数和内容一致性

**完成表现：** 同一简历在编辑器、只读预览和 PDF 中内容及分页基本一致。

### 阶段 1：JD → JobProfile 最小闭环

**目的：** 建立整个 V2.0 的统一评价标准。

- 用户粘贴并保存 JD
- AI 提取岗位名称、职级、行业、职责、必备能力、加分项和关键词
- 每项要求保留 JD 原文证据
- 用户可以修改并确认岗位画像
- 保存 `parserVersion`、`promptVersion` 和 JobProfile 版本

**页面呈现：** 左侧 JD 原文，右侧结构化岗位画像；低置信度字段提示用户确认。

**验证重点：** 结构化结果是否准确、用户是否理解并愿意确认，而不是模型输出是否看起来丰富。

### 阶段 2：ATS 与岗位匹配

**目的：** 让用户知道简历哪里有问题，以及为什么有问题。

- ATS 基础分：结构完整性、可解析性、日期一致性、内容表达等
- 岗位匹配分：能力覆盖、关键词证据、职责相关性和职级匹配
- 两类分数独立展示
- 问题定位到具体 `section / item / field`
- 区分“已匹配、证据不足、能力缺口、待确认”

**页面呈现：** 总览分数只是入口，主要区域展示可定位、可处理的问题清单；点击问题跳转到对应简历字段。

**实现原则：** 大模型负责抽取与语义判断，确定性规则负责可复现评分。当前单份 JD 与简历对比不强制使用向量库。

### 阶段 3：基于问题的定制优化

**目的：** 从“给一段润色结果”升级为可控的修改工作流。

- 针对某个 ATS 或匹配问题发起优化
- 展示修改前、建议文本、修改理由和对应 JD 证据
- 支持逐条接受、拒绝和手动调整
- 缺少事实时转为追问用户，不编造经历
- 应用建议前自动创建版本快照

**页面呈现：** 编辑器右侧为诊断与建议面板，接受建议后立即重新评分，并展示变化原因。

**核心指标：** 建议采纳率、采纳后问题解决率、用户撤销率。

### 阶段 4：版本管理与效果验证

**目的：** 让优化过程可恢复、可比较、可解释。

- 自动快照与手动命名版本
- 版本恢复
- 字段级修改摘要或差异对比
- 展示 ATS 分、匹配分及问题数量变化
- 每个版本绑定评分器和 JobProfile 版本

**页面呈现：** 时间线展示“修改了什么、为什么修改、分数如何变化”，而不只是保存多个副本。

### 阶段 5：基于 JD 的在线面试

**目的：** 让模拟面试验证岗位能力，而不是随机聊天问答。

- 开始前选择 JobProfile 和简历版本
- 根据岗位、行业、职级与简历证据生成 Rubric 快照
- 每道题关联一个或多个能力维度
- 单题评价包含分项得分、回答证据、知识缺口和置信度
- 根据覆盖率与薄弱项动态出题
- 提供可组合的面试工作台，通过左侧导航按需打开简历、JD、面试记录等辅助面板
- 最终报告展示岗位胜任度、能力覆盖和下一步训练建议

**页面呈现：** 答题是稳定的主区域；左侧工作台导航用于切换辅助面板，岗位要求、当前考察维度和简历证据按需出现；面试后提供可追溯报告。

### 阶段 6：闭环与质量体系

**目的：** 证明各模块共享数据后确实比独立工具更有价值。

- 从面试薄弱项返回简历证据补充或专项训练
- 记录评分规则、Prompt、模型和 Rubric 版本
- 建立固定 JD/简历/回答评测集
- 增加结构化输出失败降级、限流、重试和成本观测
- 观察用户从 JD 分析到面试报告的漏斗

## 4. 简历导入的安排

简历导入很重要，但它首先是降低迁移成本的入口，不是 V2.0 的核心评价能力。建议在阶段 1 或阶段 2 验证完成后插入开发，具体优先级由“新用户因重新填写而流失”的实际情况决定。

第一版范围：

- 支持文本型 PDF 和 DOCX
- 提取为统一 `ResumeDocument`
- 原文件预览与结构化结果并排确认
- 用户确认后才创建可编辑简历
- 导入后直接进入 JD/ATS 分析闭环

暂缓范围：扫描件 OCR、复杂双栏还原、表格简历和原排版像素级复刻。

## 5. 在线面试中的简历预览

### 产品判断

简历预览重要，但不是在线面试的核心主功能。它的价值在于给用户和面试 Agent 提供一致的事实背景，避免用户忘记自己简历中的项目细节，并让追问能够指向具体证据。

如果预览占据过大空间，会分散答题注意力；如果完全没有预览，用户又难以理解“为什么问这道题”。因此建议采用按需辅助设计：

- 面试开始前：完整预览并确认本场使用的简历版本
- 面试进行中：默认折叠为侧边栏，展示当前问题关联的简历片段，而不是始终展示整份 A4 简历
- 用户需要时：打开完整只读预览，复用统一 `DocumentPreview`
- 正式模拟模式：可以关闭或限制预览，模拟不能随时翻看简历的真实场景
- 训练模式：允许查看，并明确标记本题引用的项目、经历或技能
- 面试报告：点击评价证据可以回到对应简历条目

### 可组合面试工作台

在线面试采用“稳定答题主区域 + 可组合辅助面板”的工作台布局。左侧提供面板导航，顶部或左侧的 `+` 用于添加当前未打开的系统面板。简历预览是工作台中的一种面板，而不是写死在页面中的固定区域。

```text
┌──────────────────────────────────────────────────────┐
│ 面试进度 / 当前考察维度 / 计时                  结束 │
├──────────┬───────────────────────────────────────────┤
│ 对话     │                                           │
│ 简历     │              面试答题主区域               │
│ JD       │         题目 / 回答 / 语音 / 反馈          │
│ 记录     │                                           │
│  +       │                                           │
└──────────┴───────────────────────────────────────────┘
```

第一版工作台提供以下系统面板：

| 面板 | 主要内容 | 行为 |
| ---- | -------- | ---- |
| 简历预览 | 本场锁定的简历版本 | 复用统一 `DocumentPreview`，支持定位并高亮当前问题关联条目 |
| 岗位要求 | JobProfile 的职责、能力和关键词 | 优先展示当前问题对应的评价维度与 JD 原文证据 |
| 面试记录 | 已完成的问题、回答和阶段性反馈 | 点击后定位到对应轮次，不改变 Agent 当前状态 |
| 临时笔记 | 用户个人记录 | 训练模式默认可用，正式模拟模式可关闭 |

交互约束：

- 面板可以打开、关闭、切换和折叠，主答题区域始终保持稳定
- `+` 第一版只能添加系统预定义面板，不支持任意网页、任意组件或无限创建同类窗口
- 打开简历面板时自动定位当前问题关联的项目、经历或技能；没有关联证据时保持普通完整预览
- 训练模式允许查看简历、JD 和提示；正式模拟模式可以隐藏或限制辅助面板
- 面试期间简历只读，不允许修改本场绑定的简历版本
- 切换面板不能重置问题、计时器、草稿、消息或 Agent 工作流状态

状态设计必须分离：

```text
InterviewState
├── session、currentQuestion、messages、timer
├── rubricSnapshot
├── resumeVersionId
└── jobProfileVersionId

WorkspaceState
├── openedPanels
├── activePanel
├── panelWidths
└── collapsed
```

`InterviewState` 是需要持久化和恢复的业务状态；`WorkspaceState` 只是界面布局偏好。工作台布局异常不得影响面试会话恢复。

第一版暂不实现面板拖拽停靠、同时多分屏、任意窗口布局和第三方扩展。只有固定面板模式验证有效后，再评估是否需要向自由 Canvas 演进。

### 优先级

| 能力 | 优先级 | 原因 |
| ---- | ------ | ---- |
| 锁定本场简历版本 | P0 | 保证问题、评价和报告引用同一事实来源 |
| 左侧工作台导航与面板开关 | P1 | 统一承载简历、JD 和面试记录，保持主答题区域稳定 |
| 显示当前问题关联的简历片段 | P1 | 直接帮助理解追问来源，产品价值高 |
| 打开完整只读简历 | P1 | 有用但不应占据主界面 |
| `+` 添加预定义系统面板 | P1 | 允许用户按需配置工作台，同时控制第一版复杂度 |
| 面试内完整分页与缩放操作 | P2 | 可复用现有组件，不值得单独复杂开发 |
| 自由拖拽、停靠和多分屏 | P3 | 实现成本高，待固定面板模式验证后再决定 |
| 面试时编辑简历 | 不支持 | 会破坏本场评价基准，应在面试结束后修改并创建新版本 |

## 6. 当前建议顺序

在简历预览基础能力已经统一后，下一步建议是：

1. 完成 JD 保存、解析、JobProfile 确认的前后端纵向切片
2. 用少量真实 JD 建立解析评测样本并调整结构
3. 实现第一版确定性 ATS 规则与问题定位
4. 实现岗位匹配，但保持和 ATS 分数分离
5. 根据用户迁移阻力决定插入简历导入，或继续做局部优化
6. 完成版本快照后，再让在线面试绑定固定简历版本与 JobProfile

不要提前锁死后续阶段。完成每一项后，都应根据验证记录重新评估下一项是否仍然最重要。

## 7. 候选需求池

以下需求暂不承诺具体版本顺序：

- OCR 与复杂简历导入
- 招聘平台 JD 自动抓取或浏览器插件
- 多份 JD 的岗位聚类和批量投递分析
- 向量检索与长期能力记忆
- 语音面试、摄像头和非语言表现分析
- 企业 HR 端和多人协作

只有当现有闭环出现明确瓶颈或用户反馈证明价值时，再将候选需求移入当前迭代。
