# ResumePilot V2.0 开发路线图

**文档性质：** 动态执行文档  
**对应产品文档：** [AI 简历助手开发文档](./AI%20简历助手开发文档.md)  
**当前目标：** 验证“JD 分析—简历优化—版本验证—面试训练—个人能力复盘”求职闭环，而不是一次性完成全部功能。

## 1. 维护规则

本路线图允许频繁调整，不把第一次设计当作最终答案。

- 每完成一个可使用的纵向切片，就进行一次真实简历和真实 JD 验证
- 根据用户价值、技术风险和验证结果重新排序，不按模块机械开发
- 每次只保持一个主要开发目标，其他需求进入候选池
- 产品范围和验收口径写入产品文档；开发顺序、方案实验和复盘记录在本文档
- 评分规则、Prompt、JobProfile 和 Rubric 必须带版本号，确保调整后结果可追踪
- 新功能先证明闭环价值，再补充复杂自动化、向量检索或爬虫

每轮迭代结束记录：

| 项目 | 内容 |
| ---- | ---- |
| 本轮假设 | 希望解决的用户问题及预期结果 |
| 最小实现 | 本轮实际交付的最小闭环 |
| 验证样本 | 使用了哪些岗位、JD 和简历 |
| 观察指标 | 完成率、修改采纳率、评分变化、面试完成率等 |
| 发现的问题 | 用户困惑、错误结果、性能或成本问题 |
| 调整决定 | 保留、修改、降级、推迟或删除 |
| 下一轮目标 | 下一项最值得验证的能力 |

## 2. V2.0 最终呈现

V2.0 不再以零散 AI 工具为中心，而以一次“目标岗位求职任务”为中心：

```text
创建或导入简历
      ↓
粘贴 JD → 确认岗位画像 JobProfile
      ↓
ATS 基础分析 + JD 岗位匹配
      ↓
定位问题 → 局部优化 → 用户确认
      ↓
保存简历版本 → 对比优化前后结果
      ↓
基于同一 JobProfile 和简历版本进行模拟面试
      ↓
生成能力报告 → 返回简历或继续专项训练
      ↓
个人中心沉淀评分趋势与用户能力画像
```

当前导航结构：

- 我的简历：创建、导入、编辑、预览和版本管理
- 目标岗位：保存 JD、确认岗位画像和查看匹配结果
- 模拟面试：直接进入面试准备/进行界面，在同一路由内选择目标岗位与简历版本后开始训练
- 面试记录：只查看面试训练与报告；简历版本和岗位分析记录分别归属“我的简历”和“目标岗位”
- 个人中心：通过导航栏头像进入，展示跨记录聚合的评分趋势、能力画像和账户信息

导航与路由规则详见 [V2.0 信息架构与界面规范](./V2.0信息架构与界面规范.md)。普通管理页面始终显示全局导航；简历编辑器和模拟面试状态机使用精简任务工具栏；登录页与 PDF 渲染页不显示全局导航。ATS、内容质量与岗位匹配属于“目标岗位”的二级能力，不单独占用一级导航。

## 3. 开发阶段

路线图采用纵向切片。每一阶段都必须形成用户可体验的结果，阶段顺序可根据验证结果调整。

### 阶段 0：稳定简历基础能力

**目的：** 确保后续所有分析引用同一份可靠的简历数据。

**状态：** 进行中

- 统一 `ResumeDocument` 数据结构
- 编辑器、首页、在线面试复用同一预览内核
- 修复 A4 分页、模板渲染和 PDF 导出一致性
- 建立关键模板与分页的回归样本

当前实施记录：

- 已统一编辑器、首页、在线面试的 React 预览内核
- 已启动 PDF 导出链路统一：Puppeteer 打印专用只读预览路由，不再使用独立旧 HTML 模板
- 下一步补充模板/分页回归样本，并验证浏览器预览与实际 PDF 页数和内容一致性

**完成表现：** 同一简历在编辑器、只读预览和 PDF 中内容及分页基本一致。

### 阶段 1：JD → JobProfile 最小闭环

**目的：** 建立整个 V2.0 的统一评价标准。

**状态：** 进行中

- 用户粘贴并保存 JD
- AI 提取岗位名称、职级、行业、职责、必备能力、加分项和关键词
- 每项要求保留 JD 原文证据
- 用户可以修改并确认岗位画像
- 保存 `parserVersion`、`promptVersion` 和 JobProfile 版本

**页面呈现：** 左侧 JD 原文，右侧结构化岗位画像；低置信度字段提示用户确认。

当前实施记录：

- 已完成 JD 保存、列表、删除以及 JobProfile 生成、修改、确认和版本替换流程
- 已保存模型、Prompt、Parser 和 JobProfile 版本信息
- 已提供岗位画像版本列表与切换，明确标记“待确认、当前确认、历史版本”；重新分析会冻结旧草稿，历史版本只读
- 已强制校验职责、必备能力和加分项的证据必须能在 JD 原文中定位
- 低于 70% 置信度的提取项在确认页面标记为“需要重点确认”
- 已建立结构校验、代码块兼容、关键词去重和虚假证据拒绝的解析回归测试
- 待使用多份真实 JD 与实际模型完成产品验收后，再将阶段 1 标记为完成

**验证重点：** 结构化结果是否准确、用户是否理解并愿意确认，而不是模型输出是否看起来丰富。

### 阶段 2：ATS 与岗位匹配

**目的：** 让用户知道简历哪里有问题，以及为什么有问题。

**状态：** 进行中

- ATS 结构分：机器可读性、字段完整性、日期格式和明显无意义文本，只使用可复现规则
- 内容质量分：连贯性、信息有效性、任务—行动—结果表达和上下文一致性，由语义评价 Agent 生成字段级结论与置信度
- 岗位匹配分：能力覆盖、关键词证据、职责相关性和职级匹配，只使用已确认 JobProfile
- 结构分、内容质量分、岗位匹配分独立展示，禁止把“字段填满”呈现为“内容优秀”
- 事实可信度不混入语言质量：院校、公司等实体只有在接入权威数据源后才能标记“已核验 / 未找到 / 待确认”，不能让大模型直接判断造假
- 问题定位到具体 `section / item / field`
- 区分“已匹配、证据不足、能力缺口、待确认”

内容质量 Agent 的评价维度：

- 语言连贯性：是否为完整、可理解的自然语言，而非字符堆叠
- 信息有效性：是否提供求职相关信息，而非空泛自评或无意义填充
- 证据具体性：是否说明任务、行动、技术使用场景和结果
- 上下文一致性：职业目标、技能、教育、经历之间是否明显矛盾
- 表达专业性：是否存在大段重复、口语化占位、夸张但无法定位证据的表述

内容质量 Agent 的输出约束：

- 每项结论必须携带 `section / item / field`、字段原文、理由、严重级别和置信度
- 评价结果保存 `modelVersion / promptVersion / evaluatorVersion`
- 低置信度结论进入“待确认”，不直接扣除或增加最终质量分
- 模型调用失败时只展示 ATS 结构分，不得用字符规则伪装成语义评价
- 结构分、内容质量分和岗位匹配分不合并成一个来源不明的总分

阶段 2 验收数据集必须包含：完整优秀简历、字段齐全但语义无效简历、重复/乱码文本、虚构但语言正常的实体、跨字段矛盾、缺少 JD 证据和不同年限岗位样本。

**页面呈现：** 总览分数只是入口，主要区域展示可定位、可处理的问题清单；点击问题跳转到对应简历字段。

**实现原则：** 确定性规则负责结构分；大模型负责内容质量与岗位语义判断，但必须返回字段定位、理由和置信度；权威数据源负责实体核验。三层结论分别保存、分别版本化。当前单份 JD 与简历对比不强制使用向量库。

当前实施记录：

- 已完成 ATS 基础体检首个纵向切片：用户在目标岗位页选择简历并主动运行分析
- 已建立 `ats-rules-v3-additive` 确定性加分评分器：从 0 分开始，按机器可读性、基本信息、教育信息、经历证据、专业技能和内容表达六个维度获得分数；空白与空壳模块天然不得分
- 已将当前结果明确降级命名为“ATS 结构初检”，展示评价边界；增加重复字符、占位词和键盘乱码等明显无意义文本拦截
- 已完成内容质量评价 Agent 首个纵向切片：独立评价连贯性、信息有效性、证据具体性、上下文一致性和表达专业性，不与 ATS 结构分合并
- 内容质量问题已绑定简历 `section / item / field`、字段原文、理由、建议、严重级别和置信度；低于 70% 的结论标记为“待确认”
- 已保存简历更新时间、内容哈希、模型、Prompt 和评价器版本；简历修改后旧报告标记为过期
- 已强制校验模型引用的字段及证据必须能在简历原文中定位，拒绝模型编造证据；模型失败时不生成替代语义分
- 每个问题均返回明确扣分及 `section / item / field` 定位，可进入编辑器对应模块处理
- ATS 基础分与岗位画像确认解耦；JD 岗位匹配仍要求使用已确认 JobProfile
- 仍需在模型服务恢复可用后，使用真实模型和固定异常简历集完成内容质量评价校准
- 已完成基于当前已确认 JobProfile 的岗位匹配首个纵向切片：能力覆盖、职责相关性、关键词证据和职级匹配四维独立计分，逐项区分“已匹配、证据不足、能力缺口、待确认”，并保存画像版本、简历更新时间、模型、Prompt 与评价器版本
- 岗位匹配由后端强制选择当前已确认画像；模型引用的简历证据必须能定位到具体字段连续原文，低于 70% 置信度的结论只能进入“待确认”；画像或简历更新后历史报告标记为过期
- 真实模型内容质量固定集已完成 5/5 校准：能够区分优秀内容、语义填充、乱码重复、实体真实性边界和跨字段矛盾；当前模型单样本耗时约 45–73 秒
- 岗位匹配 Prompt 已升级到 `job-match-v2`：技能栏中的裸关键词只能判定为“证据不足”，必须有经历或项目中的使用场景才能判定“已匹配”；该异常样本真实模型复测通过
- 当前 SiliconFlow/Kimi K2.6 存在明显尾延迟：短连接约 3 秒，但结构化评价偶发超过 180 秒；完整岗位匹配固定集仍需在服务稳定后再次执行最终验收
- 院校真实性核验作为独立数据能力设计：优先使用可维护的院校标准库，无法命中时只标记“待确认”，不直接判定虚假

### 阶段 3：基于问题的定制优化

**目的：** 从“给一段润色结果”升级为可控的修改工作流。

- 针对某个 ATS 或匹配问题发起优化
- 展示修改前、建议文本、修改理由和对应 JD 证据
- 支持逐条接受、拒绝和手动调整
- 缺少事实时转为追问用户，不编造经历
- 应用建议前自动创建版本快照

**页面呈现：** 编辑器右侧为诊断与建议面板，接受建议后立即重新评分，并展示变化原因。

**核心指标：** 建议采纳率、采纳后问题解决率、用户撤销率。

### 阶段 4：版本管理与效果验证

**目的：** 让优化过程可恢复、可比较、可解释。

- 自动快照与手动命名版本
- 版本恢复
- 字段级修改摘要或差异对比
- 展示 ATS 分、匹配分及问题数量变化
- 每个版本绑定评分器和 JobProfile 版本

**页面呈现：** 时间线展示“修改了什么、为什么修改、分数如何变化”，而不只是保存多个副本。

### 阶段 5：基于 JD 的在线面试

**目的：** 让模拟面试验证岗位能力，而不是随机聊天问答。

- 开始前选择面试岗位目标和简历版本；岗位目标从已确认的 JobProfile 中选择，默认值为“通用岗位”
- “通用岗位”使用系统内置通用 Rubric，并在面试页和最终报告中明确标记，不能伪装为具体 JD 定向面试
- 根据岗位、行业、职级与简历证据生成 Rubric 快照
- 每道题关联一个或多个能力维度
- 面试过程中只记录问题与回答，不展示评分、评论、答案优劣或改进建议
- 下一题根据预设面试计划、能力覆盖情况和回答内容决定，不依赖尚未生成的正式评分
- 结束面试后，将完整问答记录和 Rubric 快照一次性提交评价流程
- 报告生成阶段再产生逐题证据、分项得分、知识缺口、置信度和综合建议
- 提供可组合的面试工作台，通过左侧导航按需打开简历、JD、面试记录等辅助面板
- 最终报告展示岗位胜任度、能力覆盖和下一步训练建议

**页面呈现：** 答题是稳定的主区域；左侧工作台导航用于切换辅助面板，岗位要求、当前考察维度和简历证据按需出现。提交回答后直接进入下一题，不插入 AI 评论；结束后进入“报告生成中”，完成后统一展示可追溯评价报告。

调整后的面试流程：

```text
选择 JobProfile 与简历版本
        ↓
生成并冻结 InterviewPlan 与 Rubric
        ↓
提问 → 保存回答 → 决定下一题 → 继续提问
        ↓                    ↑
        └──── 过程中不评分、不评论 ────┘
        ↓
用户结束面试 / 达到题目数量
        ↓
完整问答记录 + Rubric → Evaluation Agent 批量评价
        ↓
后端校验并计算总分 → 写入逐题评价与最终报告
        ↓
历史记录保存原始报告 → 个人中心更新聚合画像
```

评价任务失败时，面试会话进入“报告生成失败/可重试”状态，完整问题和回答不得丢失，也不得退回即时评论模式。

### 阶段 6：个人中心与用户能力画像

**目的：** 将分散在 ATS、岗位匹配、简历优化和模拟面试中的结果沉淀为可持续观察的个人求职数据，而不是只保留一次性报告。

- 通过导航栏头像进入个人中心，不新增拥挤的一级文字导航
- 展示面试次数、平均分、最近得分和阶段趋势
- 展示 ATS 基础分、岗位匹配度和简历优化前后变化
- 根据多次已完成评价聚合技术能力、表达能力、项目深度和岗位适配等维度
- 形成用户能力画像，标注数据来源、样本数、置信度和最近更新时间
- 展示近期活动，并能跳转到对应面试报告、ATS 分析或简历版本
- 支持基础账户信息、模型配置入口和数据隐私说明

**页面呈现：** 顶部是个人信息与求职目标；中部展示核心数据卡片和趋势图；下方展示能力画像与近期活动。样本不足时展示“数据不足”，不生成虚假的精确结论。

个人中心与历史记录的边界：

- 历史记录保存“每一次发生了什么”，负责查看和追溯原始报告
- 个人中心回答“长期来看发生了什么变化”，负责聚合、趋势和用户画像

用户画像约束：

- 只使用用户明确填写的信息及系统正式评价结果
- 不从一次面试推断稳定能力，不推断性格、健康、身份等敏感属性
- 不同岗位画像分开统计，不能把前端岗位得分直接混入后端岗位能力结论
- 删除原始评价后，对应聚合数据必须重新计算

### 阶段 7：闭环与质量体系

**目的：** 证明各模块共享数据后确实比独立工具更有价值。

- 从面试薄弱项返回简历证据补充或专项训练
- 记录评分规则、Prompt、模型和 Rubric 版本
- 建立固定 JD/简历/回答评测集
- 增加结构化输出失败降级、限流、重试和成本观测
- 观察用户从 JD 分析到面试报告的漏斗

## 4. 简历导入的安排

简历导入很重要，但它首先是降低迁移成本的入口，不是 V2.0 的核心评价能力。建议在阶段 1 或阶段 2 验证完成后插入开发，具体优先级由“新用户因重新填写而流失”的实际情况决定。

第一版范围：

- 支持文本型 PDF 和 DOCX
- 提取为统一 `ResumeDocument`
- 原文件预览与结构化结果并排确认
- 用户确认后才创建可编辑简历
- 导入后直接进入 JD/ATS 分析闭环

暂缓范围：扫描件 OCR、复杂双栏还原、表格简历和原排版像素级复刻。

## 5. 在线面试中的简历预览

### 产品判断

简历预览重要，但不是在线面试的核心主功能。它的价值在于给用户和面试 Agent 提供一致的事实背景，避免用户忘记自己简历中的项目细节，并让追问能够指向具体证据。

如果预览占据过大空间，会分散答题注意力；如果完全没有预览，用户又难以理解“为什么问这道题”。因此建议采用按需辅助设计：

- 面试开始前：完整预览并确认本场使用的简历版本
- 面试进行中：默认折叠为侧边栏，展示当前问题关联的简历片段，而不是始终展示整份 A4 简历
- 用户需要时：打开完整只读预览，复用统一 `DocumentPreview`
- 正式模拟模式：可以关闭或限制预览，模拟不能随时翻看简历的真实场景
- 训练模式：允许查看当前问题关联的项目、经历或技能，但不展示答案评价和提示性评论
- 面试报告：点击评价证据可以回到对应简历条目

### 可组合面试工作台

在线面试采用“稳定答题主区域 + 可组合辅助面板”的工作台布局。左侧提供面板导航，顶部或左侧的 `+` 用于添加当前未打开的系统面板。简历预览是工作台中的一种面板，而不是写死在页面中的固定区域。

```text
┌──────────────────────────────────────────────────────┐
│ 面试进度 / 当前考察维度 / 计时                  结束 │
├──────────┬───────────────────────────────────────────┤
│ 对话     │                                           │
│ 简历     │              面试答题主区域               │
│ JD       │             题目 / 回答 / 语音             │
│ 记录     │                                           │
│  +       │                                           │
└──────────┴───────────────────────────────────────────┘
```

第一版工作台提供以下系统面板：

| 面板 | 主要内容 | 行为 |
| ---- | -------- | ---- |
| 简历预览 | 本场锁定的简历版本 | 复用统一 `DocumentPreview`，支持定位并高亮当前问题关联条目 |
| 岗位要求 | JobProfile 的职责、能力和关键词 | 优先展示当前问题对应的评价维度与 JD 原文证据 |
| 面试记录 | 已完成的问题和用户回答 | 点击后定位到对应轮次，不显示评分或评论，不改变 Agent 当前状态 |
| 临时笔记 | 用户个人记录 | 训练模式默认可用，正式模拟模式可关闭 |

交互约束：

- 面板可以打开、关闭、切换和折叠，主答题区域始终保持稳定
- `+` 第一版只能添加系统预定义面板，不支持任意网页、任意组件或无限创建同类窗口
- 打开简历面板时自动定位当前问题关联的项目、经历或技能；没有关联证据时保持普通完整预览
- 训练模式允许查看简历、JD 和提示；正式模拟模式可以隐藏或限制辅助面板
- 模拟面试过程中不展示逐题评价；只有结束整场面试后才能查看统一报告
- 面试期间简历只读，不允许修改本场绑定的简历版本
- 切换面板不能重置问题、计时器、草稿、消息或 Agent 工作流状态

状态设计必须分离：

```text
InterviewState
├── session、currentQuestion、messages、timer
├── interviewPlan、coveredDimensions
├── rubricSnapshot
├── resumeVersionId
└── jobProfileVersionId

WorkspaceState
├── openedPanels
├── activePanel
├── panelWidths
└── collapsed
```

`InterviewState` 是需要持久化和恢复的业务状态；`WorkspaceState` 只是界面布局偏好。工作台布局异常不得影响面试会话恢复。

第一版暂不实现面板拖拽停靠、同时多分屏、任意窗口布局和第三方扩展。只有固定面板模式验证有效后，再评估是否需要向自由 Canvas 演进。

### 优先级

| 能力 | 优先级 | 原因 |
| ---- | ------ | ---- |
| 锁定本场简历版本 | P0 | 保证问题、评价和报告引用同一事实来源 |
| 纯问答模式与完整记录 | P0 | 避免即时评论打断面试节奏，并为结束后的统一评价保留事实 |
| 面试结束后批量评价 | P0 | 使用完整上下文和固定 Rubric 生成一致、可追溯的报告 |
| 左侧工作台导航与面板开关 | P1 | 统一承载简历、JD 和面试记录，保持主答题区域稳定 |
| 显示当前问题关联的简历片段 | P1 | 直接帮助理解追问来源，产品价值高 |
| 打开完整只读简历 | P1 | 有用但不应占据主界面 |
| `+` 添加预定义系统面板 | P1 | 允许用户按需配置工作台，同时控制第一版复杂度 |
| 面试内完整分页与缩放操作 | P2 | 可复用现有组件，不值得单独复杂开发 |
| 自由拖拽、停靠和多分屏 | P3 | 实现成本高，待固定面板模式验证后再决定 |
| 面试时编辑简历 | 不支持 | 会破坏本场评价基准，应在面试结束后修改并创建新版本 |

## 6. 当前建议顺序

在简历预览基础能力已经统一后，下一步建议是：

1. 完成 JD 保存、解析、JobProfile 确认的前后端纵向切片
2. 用少量真实 JD 建立解析评测样本并调整结构
3. 实现第一版确定性 ATS 规则与问题定位
4. 实现岗位匹配，但保持和 ATS 分数分离
5. 根据用户迁移阻力决定插入简历导入，或继续做局部优化
6. 完成版本快照后，再让在线面试绑定固定简历版本与 JobProfile，并改为结束后统一评价
7. 积累足够评价记录后实现个人中心聚合数据和用户能力画像

不要提前锁死后续阶段。完成每一项后，都应根据验证记录重新评估下一项是否仍然最重要。

## 7. 候选需求池

以下需求暂不承诺具体版本顺序：

- OCR 与复杂简历导入
- 招聘平台 JD 自动抓取或浏览器插件
- 多份 JD 的岗位聚类和批量投递分析
- 向量检索与长期能力记忆
- 语音面试、摄像头和非语言表现分析
- 企业 HR 端和多人协作

只有当现有闭环出现明确瓶颈或用户反馈证明价值时，再将候选需求移入当前迭代。
