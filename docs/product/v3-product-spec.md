# ResumePilot 3.0 产品设计与范围基线

**文档性质：** 3.0 产品范围与验收口径的权威来源  
**实施顺序：** [3.0 实施路线图](../roadmap/v3-roadmap.md)  
**集中验收：** [3.0 验收清单](../testing/v3-acceptance-checklist.md)  
**前置基线：** [现有产品基线](./product-baseline.md)

## 1. 产品定义

ResumePilot 3.0 从“提供若干 AI 求职工具”升级为“围绕目标岗位持续训练的 AI 求职教练”。系统以一次求职目标为主线，连接岗位理解、简历诊断、证据优化、模拟面试、能力复盘与下一步行动。

3.0 不以 Agent 数量、模型复杂度或页面数量衡量成功，而以用户是否能完成并重复以下闭环衡量：

```text
建立目标岗位
  → 选择岗位专属简历
  → 识别最重要的差距
  → 完成可验证的优化或训练任务
  → 重新分析并看到变化
  → 从面试结果生成下一轮行动
```

## 2. 目标用户与核心问题

### 2.1 目标用户

- 有明确目标岗位，正在准备投递或面试的求职者
- 已有基础简历，但不知道如何针对 JD 修改的求职者
- 希望通过重复模拟面试观察真实进步，而非只获取一次评分的求职者

3.0 首期不针对招聘方、猎头、企业 HR、校园就业管理机构或多人协作团队设计。

### 2.2 核心问题

1. 用户看到了许多分析结果，却不知道下一步最值得做什么。
2. 简历、岗位、优化记录、面试和能力画像之间缺少统一上下文。
3. 一次评分无法说明用户是否进步，也无法形成持续训练理由。
4. AI 建议可能缺少依据、引入虚构事实，或无法验证修改是否有效。
5. 文字面试无法训练即时表达、语速、停顿和口头禅等真实面试能力。

## 3. 3.0 产品目标

### G1：建立岗位级求职闭环

每个目标岗位都拥有独立工作空间，关联 JD、确认后的 JobProfile、岗位专属简历、诊断结果、优化历史、面试记录和行动计划。

### G2：把分析转化为可执行行动

系统根据严重程度、目标岗位相关性、证据可靠性和预期收益生成有限、可解释的下一步行动。用户完成行动后可以验证问题是否解决。

### G3：提供可恢复、可追踪的 AI 修改

所有会改变简历内容的 AI 操作必须展示依据，经过用户确认，应用前创建快照，并记录结果与撤销状态。

### G4：形成长期能力成长记录

面试评价必须关联题目、回答和 Rubric 证据。系统按同一岗位画像聚合多次训练，展示趋势、薄弱项和建议训练任务。

### G5：完成语音面试的可靠首版

首版采用按轮录音模式，完成 AI 提问播报、用户录音、转写确认、回答提交、语音表现分析和报告生成。实时全双工通话不是首版交付条件。

### G6：达到可发布产品的可靠性底线

关键流程具备加载、空状态、失败恢复、幂等、隐私说明、可观测性和自动化回归，不以演示环境中的单次成功作为验收依据。

## 4. 非目标

3.0 明确不做以下内容：

- 自动投递职位、代替用户联系招聘方或自动回复消息
- 招聘方 ATS、人才库、企业协作与权限体系
- 职位爬虫、全网岗位聚合和公司真实性调查
- 使用大模型断言学历、公司、经历或候选人是否造假
- 自动补造用户未提供的数字、职责、技术、项目成果或个人经历
- 通用简历版本树、版本分支、多人实时协作编辑
- 首期视频面试、表情识别、情绪识别或外貌评价
- 首期低延迟全双工语音、电话接入、数字人面试官
- 为制造技术复杂度而新增无法证明用户价值的 Agent、向量检索或消息队列
- 在缺少真实用户验证前建设复杂订阅、企业计费与增长裂变系统

## 5. 核心对象与归属

| 对象 | 职责 | 关键约束 |
| --- | --- | --- |
| 求职目标 `ApplicationWorkspace` | 聚合一次目标岗位求职上下文 | 必须属于当前用户；删除策略需明确级联与保留范围 |
| 岗位画像 `JobProfile` | 统一分析与面试评价标准 | 只有已确认版本可驱动岗位匹配与定向面试 |
| 岗位简历关联 | 指定该岗位当前使用的简历 | 面试开始时冻结不可变快照，不随编辑器实时变化 |
| 行动项 `ActionItem` | 表达下一步可执行任务 | 必须包含来源、原因、优先级、目标对象和完成条件 |
| 诊断/建议 | 定位问题并提供候选修改 | 结论绑定证据、版本与置信度；建议不能直接改写数据 |
| 面试场次 | 保存问题、回答、评价和流水线状态 | 重试幂等；生成失败不得丢失已保存回答 |
| 语音回答 | 保存音频元数据、转写与用户确认状态 | 内容评分基于用户确认文本；原始音频可单独删除 |
| 能力证据 | 连接能力项、题目、回答和评价 | 无可定位证据不得展示为确定性结论 |

数据库命名可在实施阶段调整，但对象职责和边界不得被弱化。

## 6. 主要体验设计

### 6.1 求职工作台

工作台回答三个问题：当前目标是什么、主要差距是什么、下一步做什么。

首屏必须包含：

- 当前目标岗位与准备状态
- 当前岗位简历及报告新鲜度
- 不超过 3 个优先行动项
- 最近一次简历优化或面试带来的可解释变化
- 继续上次任务的明确入口

不得把工作台设计为所有统计数字和功能入口的集合。没有数据时，以创建目标岗位和选择简历为唯一主路径。

### 6.2 岗位工作空间

一个工作空间至少聚合：

- JD 与已确认 JobProfile
- 当前岗位专属简历
- ATS、内容质量、岗位匹配结果及是否过期
- 优化行动和效果记录
- 文字/语音面试记录
- 求职阶段与用户备注

跨岗位的数据不得默认混合。用户切换岗位时，页面必须清楚显示上下文已经变化。

### 6.3 行动系统

行动项状态限定为 `todo / in_progress / completed / dismissed / stale`。系统生成的行动必须满足：

- 来源可追踪到诊断问题、面试弱项或用户手动创建
- 有具体对象，例如某个字段、某项能力或某类面试题
- 有明确完成条件，不使用“继续提升”“完善一下”等不可验收描述
- 完成后触发确定性检查、重新分析或用户确认之一
- 上游简历、JobProfile 或报告改变后，可判定并标记为过期

优先级算法首版使用可解释规则，不由大模型直接输出一个不可解释的综合优先级。

### 6.4 语音模拟面试

首版流程：

```text
设备与权限检查
  → AI 文字及语音提问
  → 用户录音
  → 上传并转写
  → 用户确认或修正文本
  → 提交回答并进入下一题
  → 内容评价 + 语音表现评价
  → 报告与专项训练行动
```

约束：

- 内容分与语音表现分必须分开，口音不作为负面评价依据
- 转写原文和用户确认文本分别保存，内容评价只使用确认文本
- 语音评价首版只覆盖可测指标：时长、语速、静音段、可配置口头禅和回答完整度
- 不推断情绪、人格、诚信、健康状况或受保护属性
- 未获得麦克风权限或语音服务不可用时，可降级为文字回答
- 用户可删除原始音频而保留文字面试记录；删除后不可继续展示依赖音频的复算能力

### 6.5 成长画像

- 只聚合同一确认岗位画像或明确兼容的画像版本
- 少于规定的最小有效场次数时展示“样本不足”，不生成稳定趋势结论
- 每个薄弱项必须能展开查看样本场次、题目、回答片段和评分依据
- 画像更新应记录算法、Rubric、模型和时间范围版本
- 趋势只比较可比版本；不可比时明确断点，不伪造连续曲线

## 7. 全局边界约束

### 7.1 AI 与事实安全

- 用户事实和 JD 证据必须可定位；缺少事实时追问或保留缺口
- 模型输出经过结构校验、证据校验和权限校验后才能持久化
- 低置信度结论只能进入待确认，不得自动扣分或自动修改
- 模型调用失败不得以简单字符规则伪装成语义评价
- Prompt、模型、评分器、Rubric 和输入快照必须版本化

### 7.2 数据一致性

- 分析结果必须绑定简历内容哈希与 JobProfile 版本
- 上游对象变化后，下游报告和行动必须标记过期
- 简历写入使用事务、并发保护和应用前快照
- 重试接口必须幂等，不能重复创建报告、扣减配额或覆盖新数据
- 跨用户资源访问统一返回无权限或不存在，不泄露对象存在性

### 7.3 隐私与数据生命周期

- 录音前明确说明用途、保存范围和删除方式
- 日志不得记录访问令牌、模型密钥、完整简历、完整 JD 或音频内容
- 原始音频、转写、报告和账户删除策略分别定义并可测试
- 用户配置的模型服务必须提示数据将发送到相应第三方
- 产品不得默认把用户内容用于公共训练数据集或公开样本

### 7.4 性能与降级

- 普通业务接口不等待长耗时模型任务完成
- AI 长任务提供阶段进度、失败节点、重试和恢复能力
- 语音合成失败时继续显示文字问题；转写失败时允许重试或切换文字输入
- 仪表盘聚合不得在每次打开页面时重新调用大模型
- 性能指标按部署环境建立基线，不用本地单次结果冒充线上 SLA

### 7.5 UI 与可访问性

- 桌面端为 3.0 主要体验；移动端至少可查看、录音回答和恢复任务
- 所有核心操作可通过键盘完成，表单和录音控件有可识别标签
- 不只使用颜色表达分数、状态和错误
- 异步过程必须提供状态、取消或安全离开说明
- 危险操作必须说明影响范围并二次确认

## 8. 成功指标与防护指标

首轮内测先建立基线，再确定增长目标。不得在无真实样本时声称已达到产品成功。

### 8.1 核心指标

- **北极星指标：** 每周完成一次“诊断/训练行动并验证结果”的活跃用户数
- 新用户建立目标岗位并关联简历的完成率
- 从诊断查看到开始执行行动的转化率
- AI 建议采纳率、采纳后问题解决率、撤销率
- 模拟面试开始率、完成率、报告查看率
- 语音面试从权限检查到成功提交首题的完成率
- 7 日内完成第二次有效训练的用户比例

### 8.2 防护指标

- AI 建议事实违规率
- 报告证据无法定位率
- 过期报告被误当作当前结果的比例
- AI 任务失败率、重试成功率和 P95 完成耗时
- 音频上传/转写失败率与原始音频删除成功率
- 用户撤销后内容恢复失败率
- 单次完整闭环的模型调用量与估算成本

## 9. 3.0 发布定义

只有同时满足以下条件，才允许标记为 ResumePilot 3.0：

1. 用户能在岗位工作空间中完成“目标岗位—专属简历—诊断—行动—验证”闭环。
2. 用户能完成一次按轮语音面试，并获得分离的内容与语音表现报告。
3. 面试薄弱项可以转化为可执行的下一步行动，并在后续训练中追踪。
4. 数据过期、版本、证据、失败恢复、隐私删除和权限边界通过集中验收。
5. 核心自动测试、浏览器主路径、真实模型校准和语音故障注入均有验收记录。
6. 至少完成一轮真实目标用户试用并记录问题；严重级别为阻断或高风险的问题清零。

仅完成页面、数据库表或 happy path 演示，不构成 3.0 发布。
